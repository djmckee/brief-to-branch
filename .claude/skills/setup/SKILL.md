# /setup

You are preparing a repository for the ticket-to-review pipeline. The output is one file, `.pipeline/repo.md`, the repo card. Every later skill and every subagent reads it before doing anything else, so it has to be accurate, short and copy-pasteable. Facts only.

Notes from the user: $ARGUMENTS

## 1. Detect the stack

Look at the files; do not guess from the folder name.

- Node and frontend: `package.json` (read `scripts`, `engines`, `workspaces`, `type`), the lockfile (`pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`, `bun.lockb`) which decides the package manager, `tsconfig.json`, framework config (`next.config.*`, `vite.config.*`, `nuxt.config.*`, `svelte.config.*`, `angular.json`, `remix.config.*`), test config (`vitest.config.*`, `jest.config.*`, `playwright.config.*`, `cypress.config.*`), lint and format config (`eslint.config.*`, `.eslintrc*`, `biome.json`, `.prettierrc*`).
- Python: `pyproject.toml` (read `[project]`, `[tool.*]`, `[build-system]`), `setup.py`, `setup.cfg`, `requirements*.txt`, `Pipfile`, `poetry.lock`, `uv.lock`, `tox.ini`, `noxfile.py`, `pytest.ini`, `conftest.py`, `manage.py` for Django, `alembic.ini`, `.python-version`, `ruff.toml`, `mypy.ini`.
- Shared: `Makefile`, `justfile`, `Taskfile.yml`, `docker-compose*.yml`, `Dockerfile`, `.gitlab-ci.yml`, `.github/workflows/*`, `.pre-commit-config.yaml`, `.env.example`, `.nvmrc`, `.tool-versions`, `CLAUDE.md`, `CONTRIBUTING.md`, `README.md`.
- Monorepo signals: `workspaces`, `turbo.json`, `nx.json`, `pnpm-workspace.yaml`, more than one `pyproject.toml`. If it is a monorepo, write one Commands table per package that has its own tests, and say which package is the default.

## 2. Find the commands

For each of these, find the exact command the project itself uses. CI config and the Makefile are the best sources, then package scripts, then the tool's defaults:

install, test (whole suite), test (one file), lint, typecheck, format, build, dev server, migrations if the project has them.

Then run the test, lint and typecheck commands once to confirm they work, and note roughly how long the suite takes. If a command fails, record the failure verbatim under Gotchas. Do not install anything or change config to make it pass. If the suite needs services (a database, Redis, a message queue), note how CI provides them.

## 3. Map the layout

Where source, tests, fixtures, migrations, API routes or views, UI components, shared types or models, scripts and docs live. The test naming pattern (`test_*.py`, `*.test.ts`, `__tests__/`) and how tests find their fixtures. Anything generated (lockfiles, `*.generated.*`, protobuf output, snapshots, built assets) so reviewers can skip it.

## 4. Record the conventions

- Commit message style, from `git log --oneline -30`. Conventional commits or not, ticket key prefix or not.
- Branch naming, from `git branch -r | head -40`.
- Default branch, from `git symbolic-ref refs/remotes/origin/HEAD`, or infer from `main`, `master`, `develop`.
- MR or PR template, if any (`.gitlab/merge_request_templates/`, `.github/pull_request_template.md`).
- Style the linter does not enforce: type hints, docstrings, the error handling pattern, the logging library, how config and secrets are read, i18n.
- Any rule in `CLAUDE.md` or `CONTRIBUTING.md` that an implementer must follow. Quote it rather than paraphrasing.

## 5. Write the repo card

Write `.pipeline/repo.md` in this shape. Keep it under 120 lines. Commands go in code spans and must run from the repo root as written.

```markdown
# Repo card

Generated by /setup on <date>. Rerun /setup if the toolchain changes.

## Stack
<language and version, framework and version, package manager, test runner, linter, typechecker, formatter, database or ORM, monorepo tool>

## Commands
| Purpose | Command | Notes |
|---|---|---|

| test (all) | `...` | about N seconds, needs X |
| test (one file) | `... <path>` | |
| lint | `...` | |
| typecheck | `...` | |
| format | `...` | |
| build | `...` | |
| dev | `...` | |
| migrate | `...` | |

## Layout
<one line per area: path, what lives there>

<pattern, fixtures, how to run one test, what is slow, what needs services>

```

## 6. Keep pipeline files out of the diff

Check `git check-ignore -q .pipeline`. If it is not ignored, add `.pipeline/` to `.gitignore` and say so. Teams that would rather commit the spec alongside the feature can remove that line later.

## 7. Report

Reply with the Stack and Commands sections and anything that failed. Ask the user to correct anything wrong, since every later step trusts this file. Suggest `/refine <ticket or idea>` as the next step.
